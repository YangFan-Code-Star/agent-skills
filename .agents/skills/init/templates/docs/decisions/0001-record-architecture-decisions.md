# 0001. 用 ADR 记录架构决策

日期：2026-08-13
状态：已接受

## 背景

代码能表达"做了什么"，表达不了"为什么不用另一个方案"。这类信息只存在于当时做决定的人脑子里，而人会忘、会离开，agent 则从一开始就没有。

后果是具体的：agent 会反复提议已经被否决过的方案，而你要一遍遍重新解释同样的理由；或者更糟——它推翻了一个当初有充分理由的设计，因为看不出那个理由。

## 决策

有取舍的技术决策写成 ADR，存在 `docs/decisions/NNNN-标题.md`，一个决策一个文件，按顺序编号。

**只增不改。** 决策变了就写新的一份，在旧的顶部标注「已被 ADR NNNN 取代」，保留原文。

判断要不要写的标准：**另一个方案是不是也说得通？** 是，就写；不是，就不用。

## 其他方案

### 方案 A：一个 `decisions.md` 追加所有决策

省文件数，但会长成一个没人读、也没法在上下文里按需加载的巨型文件。一决策一文件可以只读需要的那份，也让 git 历史清楚地对应到单个决策。

### 方案 B：写在代码注释里

离代码近是优点，但被否决的方案在代码里没有对应位置——你没法在一段不存在的代码旁边注释"我们没有这样做，因为……"。而这恰恰是最需要记录的部分。

### 方案 C：不记录，靠提交信息

提交信息面向的是"这次改了什么"，检索成本高，而且不会被 agent 主动读取。

## 后果

- 好处：agent 读得到"为什么不用 B"，不再重复提议被否决的方案；你不必反复解释同样的理由。
- 代价：每个决策多花几分钟写。缓解办法是设了门槛——没有真实取舍的选择不写。
- 新约束：ADR 不能改。这在决策频繁反复的早期会积累一些"历史文件"，属于有意的取舍：保留走过的弯路本身有价值。

## 什么情况下该重新考虑

如果 `docs/decisions/` 长期只有这一份，说明要么项目确实没有需要记录的取舍（那没问题），要么这个流程没有真正跑起来（那要么降低门槛，要么承认它不适用并删掉）。
