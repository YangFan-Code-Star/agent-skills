## 铁律

违反这几条会造成不可逆损失或让 agent 自信地干错事，优先级高于任何"看起来更简洁"的写法。

下面 6 条里，**「不确定就问」「破坏性操作先确认」「密钥和真实数据永不进仓库」默认保留**——违反它们的代价不可逆，别的条款可以事后补，这三条不能。其余三条 init 会问你要不要留。然后追加这个项目特有的红线，总数控制在 10 条以内——领域红线优先于通用条款，因为通用条款模型多少还能猜到，领域红线猜不到。

1. **不确定就问，不要编。** 任何没在仓库里读到依据的事实——API 行为、字段含义、业务口径、库的用法——先查证或先问，不要凭印象写进代码和文档。宁可停下来问一句，也不要交付一个看起来很像对的猜测。
2. **改完自己跑与改动相关的验证命令。** 改哪个模块就跑覆盖它的测试和 lint，通过再汇报。没跑就说"应该没问题"是不可接受的。全量检查只在里程碑或发版前跑，不是每次小改动的门槛。
3. **破坏性操作先确认。** `git push`、强制推送、删分支、重置历史、递归删除、清空数据库、改 `.gitignore` 放开已忽略的文件——这些在用户明确要求前一律不做。这条没有工具在背后拦你，只能靠遵守。
4. **密钥和真实数据永不进仓库。** `.env`、凭证、生产数据导出、真实个人信息，不写进代码、测试、注释、提交信息。需要示例数据时用明显虚构的值。
5. **范围纪律。** 不在 [docs/roadmap.md](docs/roadmap.md) 里的需求，先补一条再动手。修 bug 时不顺手重构，改功能时不顺手改风格，不为"以后可能要用"引入新抽象、依赖或配置文件——把无关改动留给下一个 PR。验证只跑与改动相关的命令，通过一次即止，不跑全量检查。
6. **决策留痕。** 做了有取舍的技术选择（选了 A 没选 B），写一份 ADR 到 `docs/decisions/`。代码读不出"为什么不用 B"，缺了它 agent 会反复提议已经被否决过的方案。

## 维护这份手册

这个文件会过期，而过期的手册比没有手册更糟——它会让 agent 自信地干错事。规则：

- 改了命令、目录结构、铁律、术语 → **同一个改动里**更新本文件。
- 做了有取舍的技术决策 → 加 ADR，本文件只留一行指针。
- 细节增长超过 5 行 → 移到 `docs/`，这里只留链接。
- 目标长度 150 行以内。超了就是该往 `docs/` 搬了。
- 定期体检：`node scripts/audit-context.mjs`，然后走 `/maintain-context`。
