# 访谈题库

阶段 2 用。按项目形态选一到两组，**挑真正适用的问，不要机械念完**。不适用的跳过并说明为什么跳过。

每组问题都遵循一个标准：**答案在代码里读不出来**。能从 `package.json` 或目录结构看出来的，不配出现在这里。

**提问方式：推导式优先。** 能把问题从上个答案推出来的，就说明推导再问（例："你说这是单用户本地工具 → 那没有登录鉴权 → 数据存哪？"）。清单式念题只用于确实独立、无法推导的问题。判断要不要停看文末「收敛判据」，四条全过就停，不必把题库问完。

---

## 通用追加组（每个项目都问）

不管什么形态，这 5 个问题都要问。它们决定 agent 的行为方式，而不是代码的样子。

1. **你希望我的自主程度是什么样？** 小步走、每步确认；还是给方向、一次交付一大块？（这一条直接影响后续每一次协作的体感，务必问）
2. **提交和分支怎么走？** 直接提交到主干，还是开分支走 PR？提交信息有格式约定吗？
3. **代码风格由工具决定还是靠人约定？** 有 formatter / linter 的话，风格问题一律以工具为准，不用写进文档。
4. **有 CI 吗？跑什么？** 没有的话，本地哪几个命令等价于 CI。
5. **这个项目多久没人碰会被你重新捡起来？** 一周一次和半年一次，文档详细程度的要求完全不同。

## A. Web 应用 / API 服务

1. 使用者是谁，需要登录吗？**单用户、单租户还是多租户？**（这一条决定要不要在每个查询里过滤用户身份，事后改代价极大）
2. 数据存在哪——关系库、文档库、文件还是第三方 API？现在和一年后的量级大概是多少？
3. 读多还是写多？有没有必须实时的部分（推送、协作编辑）？
4. 前后端一体还是分离？渲染策略是服务端渲染、客户端渲染还是静态生成？
5. 依赖哪些外部服务（支付、邮件、第三方登录、对象存储）？其中任何一个挂掉时，系统应该怎么表现？
6. 错误怎么暴露给用户？有没有统一的错误响应格式？
7. 部署在哪、怎么发版、怎么回滚？
8. 有没有对外承诺的接口需要保证向后兼容？版本策略是什么？
9. **哪些操作是不可逆的**（删除、扣款、发信、外发通知）？需要二次确认、软删除还是审计日志？

## B. CLI 工具

1. 谁在什么场景下敲这个命令？人在终端交互，还是被别的脚本调用？
2. 命令结构：单个命令还是子命令树？最主要的三个动作是什么？
3. 输入从哪来——参数、stdin、配置文件、环境变量？**几个来源冲突时谁优先？**
4. 输出是给人看还是给管道下游？要不要 `--json` 模式？
5. 退出码有约定吗？错误信息进 stderr 还是 stdout？
6. 有没有危险操作需要 `--dry-run` 或强制确认？
7. 要跑在哪些操作系统上？（决定路径分隔符、换行符、能不能假设有 shell）
8. 怎么分发给使用者——包管理器、单文件二进制、还是直接 clone？

## C. 数据分析 / 批处理流水线

1. 数据从哪来、什么格式、多大、多久来一批？
2. **源数据可信吗？有哪些已知的脏数据模式**（缺列、编码混乱、重复行、口径中途变过）？
3. 必须可复算吗——同样的输入必须得到同样的输出？中间结果要不要落盘缓存？
4. **单位和口径怎么定**：金额单位、时区、日期粒度、缺失值用什么表示、百分比是 0.04 还是 4？（这一组是数据项目最大的错误来源，一定要问到具体）
5. 遇到坏数据应该跳过、报错还是补默认值？**不要静默兜底**——明确下来写进铁律。
6. 输出给谁、什么形式（报表、CSV、图表、写回数据库）？
7. 跑一次多久能接受？需要支持增量处理吗？
8. 历史数据会被回溯修正吗？修正之后，之前基于旧数据得出的结论怎么处理？

## D. 库 / SDK

1. 使用者是谁，从哪里安装？
2. **公开 API 面有多大？** 哪些是对外稳定承诺，哪些是随时可改的内部实现？
3. 版本策略：遵循 semver 吗？破坏性变更怎么发布和告知？
4. 要支持哪些运行时版本 / 语言版本 / 平台？
5. 依赖策略：可以自由引入第三方依赖，还是要求零依赖或最小依赖？
6. 错误怎么交给调用方——抛异常、返回错误值、还是 Result 类型？
7. 文档和示例放在哪、谁负责跟着代码一起更新？

## E. 机器学习 / 模型训练

1. 预测任务是什么？**用什么指标评估，多少分算可用？**
2. 数据集从哪来、多大、标注质量如何、怎么划分训练验证测试？
3. **有没有数据泄漏风险**——时间序列里混入未来信息、训练集和测试集有重复样本、特征里含有目标的代理变量？
4. 训练在哪跑（本地 GPU / 云），单次多久，预算上限多少？
5. 实验怎么记录和横向对比？
6. 模型产物存在哪、怎么版本化、怎么和产生它的代码对应上？
7. 复现要求有多强？随机种子要固定吗？
8. 最终怎么用——离线批量打分还是在线推理？延迟要求？

## F. 自动化 / 脚本集合

1. 每个脚本解决的是什么重复劳动？多久跑一次？
2. 手动触发还是定时触发？**失败了谁会知道、怎么知道？**
3. 需要哪些凭证，存在哪里，谁能拿到？
4. **有没有会修改外部系统状态的操作**（发消息、改数据、下单、发邮件）？误触发一次的代价是什么？
5. 幂等吗——同一个脚本重复跑两遍会发生什么？
6. 有没有速率限制、配额或调用窗口需要注意？

## G. 通用兜底（形态不明确或跨多个分支时用）

1. **带我走一遍最典型的使用流程**，从你开始操作到拿到结果，中间每一步是什么？
2. 这个项目里最容易出错的地方是哪？
3. 有哪些"看起来可以但实际行不通"的做法？
4. 如果只能保证一件事绝对不出错，你选哪件？
5. 三个月后，你会用什么标准判断这个项目值不值得继续做？

## 追问技巧

用户给出这些回答时，**必须再追问一轮**，否则写进文档也是废话：

| 用户说 | 追问 |
| --- | --- |
| "要好用 / 要快 / 要稳定" | "能给个具体场景吗——什么情况下你会觉得它不好用？" |
| "按最佳实践来" | "有没有你见过的反面例子？我想知道你在避免什么。" |
| "都行 / 你决定" | 给出你的选择和一句理由，标注「agent 代填，待确认」，继续往下 |
| "大概吧 / 应该是" | "这个如果搞错了，会造成什么后果？"——后果大就必须问准，后果小就先用默认值 |
| 一次性说了很多需求 | 复述成条目让他确认，并追问"这里面哪一个最先要？" |

还有一个信号值得留意：**用户在解释一件事时用了"其实"、"要注意的是"、"之前踩过坑"**——后面跟着的往往是整场访谈里最有价值的信息，一定要原样记下来，通常该进 `docs/troubleshooting.md` 或变成一条铁律。
