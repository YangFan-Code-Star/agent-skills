# 维护 agent 上下文

上下文文件的失效方式不是报错，而是**安静地说谎**：命令改了它还写着旧的，描述的架构已经不存在。而 agent 会照着旧信息自信地干活。所以需要定期体检。

## 流程

```
- [ ] 1. 跑自动检查脚本
- [ ] 2. 合并学习收件箱
- [ ] 3. 核对"事实类"内容
- [ ] 4. 核对"规则类"内容
- [ ] 5. 找缺口（孵化）
- [ ] 6. 删掉过期内容
- [ ] 7. 修文件并汇报
```

### 1. 自动检查

```bash
node scripts/audit-context.mjs
```

脚本查的是机械问题：`AGENTS.md` 行数与字节数、文档链接是否有效、技能 frontmatter 是否完整、`TODO(init)` 残留、上下文文件与代码的更新时间差、敏感文件是否被忽略、学习收件箱是积压还是长期闲置。

**先把 error 全部修掉，warning 逐条判断。**

### 2. 合并学习收件箱

把项目根目录的 `docs/learning-inbox.md` 里的条目逐条处理。对每条问同一个问题：**「模型本来就猜得到吗？」** 猜得到就删掉不合并——收件箱里塞进「要写测试」这种废话，是蒸馏环节的失误。

留下的，按条目的「建议去向」写进目标文件，然后从收件箱里删掉这条（它是队列，不留历史）。

合并时别照单全收：一条「纠正」如果和现有铁律重复，就强化现有那条而不是新增；一条「坑」如果只是环境一次性问题，记在 `troubleshooting` 但别升级成铁律。

**这就是本体系唯一的数据来源——纠正信号，不靠自觉统计。** 技能触发次数、文档读取频率没有可靠的 hooks 能自动记录，任何统计文件都只会漂移；而「agent 哪里不懂、被纠正了什么、卡了多久」是任务里自然产生的，天然可靠。

### 3. 核对事实类内容

拿 `AGENTS.md` 逐行对照真实仓库：

| 声称 | 用什么核对 |
| --- | --- |
| 命令表 | 包管理文件里的 scripts / Makefile；**并且真的跑一遍** |
| 目录地图 | 实际目录，看有没有新增顶层目录没写进去 |
| 术语表 | 代码里的实际命名 |
| 架构描述 | `docs/architecture.md` 与实际的 import 关系 |
| 当前状态 | `docs/roadmap.md` 与最近的提交 |

任何不一致，**改文件，而不是改口径去迁就文件**。

### 4. 核对规则类内容

对每一条铁律问三个问题：

1. **还成立吗？** 描述的模式代码里还在用吗？换掉的技术要删掉对应规则，不要留着"历史参考"。
2. **可执行吗？** "注意性能"没法验证；"金额出现浮点数就是错的"可以验证。不可执行的改写或删掉。
3. **值这个位置吗？** `AGENTS.md` 每条铁律每次对话都花钱。只有"违反了会造成事故"的才配留下，其余降级进 `docs/`。

对每个技能问：**description 里有用户真实会说的话吗？** 宿主只靠 `name` 和 `description` 决定要不要加载正文，描述写成"帮助分析数据"这种，它永远不会被触发。

### 5. 找缺口（孵化）

下面的阈值就是孵化规则：**同一个信号第二次出现，就从对话升级成文件。** 收件箱（第 2 步）里还没到阈值的候选，留在这不动。

回顾最近的工作，出现这些信号就说明缺一份上下文：

| 信号 | 该补什么 |
| --- | --- |
| 同一个约定解释了两次以上 | 一条铁律，或 `docs/` 里的一节 |
| agent 反复犯同一个错 | 一条带 ❌/✅ 对照的铁律 |
| 一个多步流程每次都要口述 | 一个新技能 |
| "为什么不用 X"又被问了一遍 | 一份 ADR |
| 花超过 20 分钟排查的问题 | `docs/troubleshooting.md` |
| 功能范围有变 | `docs/roadmap.md` |

**agent 犯的错是免费的规则素材。** 它犯错说明上下文里缺了某句话，把那句话补上，这个错就不会再出现。这是整个体系里投入产出比最高的动作。

### 6. 删比加更重要

每次体检都该有删除动作。**过期的规则比没有规则更糟**——它会让 agent 主动做错事，而且错得很自信。

优先删这几类：换掉的技术对应的规则、已经内化成代码结构因而不必再说的约定、当时怕出错但事实上从没出过错的叮嘱、模型本来就知道的通用建议。

如果 `AGENTS.md` 超了 150 行，这一步是强制的。

## 汇报格式

```markdown
## 体检结果
脚本 error N 条、warning M 条。

## 已修
- <文件>：<改了什么，为什么>

## 已删
- <内容>：<为什么它不再值得占位置>

## 已合并
- <收件箱条目> → <目标文件>：<合并成了什么>

## 需要你确认
- <事项>：<两个选项分别意味着什么>
```

## 新增内容放哪

| 内容性质 | 位置 |
| --- | --- |
| 每次对话都要遵守 | `AGENTS.md` 铁律 |
| 多步操作流程 | `.agents/skills/<name>/SKILL.md`（并登记进 `AGENTS.md`「可用技能」表） |
| 背景知识、口径定义 | `docs/` |
| 技术决策的来龙去脉 | `docs/decisions/NNNN-*.md` |
| 机械的、可自动判定的检查 | `scripts/` 下的脚本 |
| agent 行为红线 | `.agents/evals/behavior-cases.md` |
