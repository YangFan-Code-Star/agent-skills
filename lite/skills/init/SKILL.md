# 初始化项目（轻量）

给个人 / 中小型项目用（也适合长期迭代，但不引入 PR / CL / 代码审查等团队流程）：一次只问 3 个问题，问完落盘、跑通命令、复述确认，不再有完整版的阶段 2~4。

## 访谈原则

1. **一次把 3 个问题问完，每个都给推荐答案。** 用户可以直接说"按默认"。
2. **先看再问。** 能从代码、`package.json`、`pyproject.toml`、README、`git log` 看出来的不要问，只让用户确认。
3. **用户说"不知道 / 你决定"就代填。** 给出选择 + 一句理由，标注「agent 代填，待确认」，不要卡住。
4. **只记模型猜不到的东西。** 不要把"要写测试"这类常识写进文件。

## 阶段 0：确认骨架

检查项目根 `AGENTS.md` 顶部有没有「这个仓库还没初始化」引用块：

- 有 → 继续。
- 没有，但 `AGENTS.md` 开头是本项目的一行简介、且 `docs/plan.md`、`docs/log.md` 存在 → 这已经是初始化过的轻量项目；问用户是想补哪一块，不要重头再问。
- 没有这些文件 → 骨架还没生成。让用户执行 lite 包安装步骤里的生成命令：`node <lite 包路径>/scaffold.mjs --root <项目根>`；不知道 lite 包在哪就问用户要路径，不要自己另写一份骨架。

然后读一遍现有仓库（目录、包管理文件、README、git log），把已经能确定的命令和目录填好。

## 三个问题

1. **一句话说清这个项目做什么、给谁用？**
   推荐：只有你自己用的个人小工具；按你的实际使用场景来。
2. **做到什么程度算成功 / 完成？** 给一个能验证的标准。
   推荐："能跑通 ⟨主流程⟩，并且你接下来一个月真的会用它"，或"把 ⟨重复劳动⟩ 从 X 分钟降到 Y 分钟"。
3. **从零到能跑起来、以及验证改动对不对，分别跑什么命令？**
   你给出命令，agent 与包管理文件核对后**每条真的跑一遍**再落盘。没有测试 / lint 就写"无"，不要为了好看编一个。

## 落盘

| 答案 | 写到哪 |
| --- | --- |
| 问题 1 | `AGENTS.md` 标题与开头一句话；`docs/plan.md`「一句话」 |
| 问题 2 | `docs/plan.md`「成功标准」；`docs/plan.md`「当前任务与下一步」写"先做能满足成功标准的最小版本" |
| 问题 3 | `AGENTS.md`「快速上手」与「验证命令」；`docs/plan.md`「技术与运行」；`AGENTS.md` 目录地图补齐源码目录 |

未问到的占位符**全部代填默认值，不要留 `TODO(init)`**：

- 「为什么做」：个人工具 / 中小型项目，需要长期迭代但不引入团队流程。
- 「敏感数据 / 红线」：默认不额外处理。
- 「口径与术语」「被否决的方案」：暂无，出现后再补。
- 「明确不做」：不引入与成功标准无关的功能；不做通用化、多用户、跨平台；不为"以后可能用到"加抽象和依赖。这三条让用户在最终复述时确认或改。
- 「术语」表：删掉，出现混淆词再补。
- 「当前状态」：初始化完成，正在做 `docs/plan.md` 里写的第一个任务。

最后删掉 `AGENTS.md` 顶部的引用块。

## 收尾

1. 把问题 3 的每条验证命令真的跑一遍，跑不通就修好或如实告诉用户。
2. 如果仓库里的 README 还是模板说明（讲的是 context-dev 而不是本项目），换成项目一句话简介 + 怎么装怎么跑。
3. 用一段话复述确认，不要用列表：

> 我理解你要做的是 ⟨项目一句话⟩，成功标准是 ⟨可验证标准⟩。技术上用 ⟨栈⟩，验证命令是 ⟨命令⟩。接下来先做 ⟨最小版本⟩，明确不做 ⟨三项默认排除⟩。哪里理解错了？

复述是最后一道防线：用户纠正后，把纠正同时落进对应文件再结束。
